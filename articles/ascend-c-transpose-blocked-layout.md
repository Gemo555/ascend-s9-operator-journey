# Ascend C Transpose 调优：用分块临时布局改善短片段写回

本文整理自[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)的 Transpose 赛题开发记录。题目接收输入张量和维度排列 `perm`，要求生成对应排列的输出，参考调用为 `torch.permute`。本文实现会将结果写入输出缓冲区，不能仅修改形状与步长元数据。

我们重点分析一组 FP32 输入：Shape 为 `[125,762,521]`，`perm=[0,2,1]`，输出为 `[125,521,762]`。它相当于 125 个独立矩阵，每个矩阵将 762 行、521 列转置。实验设备为 Ascend 910B4，CANN 版本为 8.5.0。

早期实现已经能连续读入源数据，再通过 Gather 得到局部转置结果，但写回仍由许多短片段组成。后来增加了一份分块临时区，先连续写入中间面板，再组装完整输出，取得了比继续微调原路径更明显的改善。本文解释这份临时布局解决了什么问题，以及它增加了哪些成本。

## 1. 局部转置完成后，输出仍然不连续

先看一个 `[M,K]` 矩阵。连续存储时，输入与输出的元素偏移满足：

```text
X[r*K + c] → Y[c*M + r]
```

若一次读取 R 行，并转置其中 C 列，UB 中会得到 C 段连续数据，每段有 R 个元素。写回到最终输出时，相邻两段的起点却相隔 M 个元素。

对于本文的 `M=762`，当 R=64 时，每段有效写入为 `64×4=256` B，相邻输出行起点相隔 `762×4=3048` B。局部转置的数据虽然已经紧凑排列，最终搬出仍需要带步长写回；把输入读取做得更连续，并没有同时解决这个问题。

还要处理最后一个行块。762 不能被 64 整除，最后一块只有 58 行。写出时需要保留这 58 个有效元素，同时避免把补齐数据带进下一输出行。

旧路径中，密集 Gather 已经减少了补齐和无效取数。继续围绕 Gather 调整，只能改善其中一段工作。我们随后把关注点转向输出组织：能否让写回由短片段变成连续的多行数据？

## 2. 将临时区组织成 `[行块, 列, 块内行]`

取行块高度 B=64，将 M 补齐为 Mₚ=768，块数为 12。为每个工作核设置一份独立 workspace，逻辑布局为：

```text
scratch: [ceil(M/B), K, B]

scratch[g, c, r] = X[g*B+r, c]
条件：g*B+r < M
```

固定 g 后，`scratch[g,:,:]` 就是这个行块的转置面板。其元素偏移与最终输出偏移分别为：

```text
scratch_offset = (g*K + c)*B + r
output_offset  = c*M + g*B + r
```

两个阶段由此分开。

第一阶段连续读入 64 行源数据，在 UB 中按 64 列小块 Gather，得到 `[64列,64行]` 的面板，再连续写入 workspace。一个完整面板的写入长度为 16 KiB，避免在这一阶段按最终输出行距写回。

第二阶段从每个行块中取出同一段列范围，将 `[行块,列,块内行]` 重排为 `[列,行块,块内行]`，再去掉最后行块中的填充。实现使用 Gatherb 重排数据块，随后用 GatherMask 压紧有效元素。

最终采用的一个配置每次组装 12 列。压紧后，它们对应输出中连续的 12 行，可以一次写出 `12×762×4=36576` B。最后不足 12 列的部分按真实长度处理。

```text
输入 GM
   ↓ 连续读取 64 行
UB 局部转置
   ↓ 连续写入面板
GM workspace：[行块, 列, 块内行]
   ↓ 读取各行块的同一段列
UB 重排、去除尾部填充
   ↓ 连续写入若干完整输出行
输出 GM
```

这条路径新增了 workspace 的一次写入和一次读取，换来了两端搬运形态的改变。忽略补齐时，算法请求的 GM 读写量由约 2D 增至约 4D；是否更快取决于访问形态、缓存和重排成本，不能只比较字节总数。

## 3. workspace 可以被缓存，但不能当作显式分配的 L2

开发记录将这条路径简称为“分块 L2”，源码类名也沿用了这个叫法。它实际申请的是 GM workspace，再通过缓存策略利用 L2，程序没有获得一块保证驻留的 L2 内存。

对于本文输入，每核 workspace 的大小为：

```text
Mₚ × K × sizeof(float)
= 768 × 521 × 4
= 1600512 B
```

同一个核处理下一个矩阵时复用这份空间，不需要为全部 125 个矩阵各保留一份。32 核对应的 workspace 合计为 51216384 B，约 48.84 MiB。

源码对源输入和最终输出设置禁用 L2 的策略，临时区保留默认缓存模式。设计动机是让短期会再次读取的中间数据有机会留在缓存中，减少大输入和最终输出对它的干扰。[SetL2CacheHint 文档](https://www.hiascend.com/document/detail/en/CANNCommunityEdition/850/API/ascendcopapi/atlasascendc_api_07_00033.html)说明了缓存开关的含义，但接口设置本身不能证明某次搬运全部命中 L2。

不能用 workspace 大小小于某个缓存容量，就断言全部中间数据常驻。实际并发访问、其他数据和替换行为都可能影响命中率。本文的性能结论来自完整计时，没有用理想缓存带宽推算加速比。

两个阶段的 UB 也不需要同时保存全部数据。第一阶段使用源行缓冲与双面板缓冲；第二阶段使用读取区、块重排区和双输出区。代码等待前一阶段的搬运结束后，让两阶段复用同一 arena，索引与掩码另行分配。这个配置的显式 UB 分配为 188288 B。

这里的复用顺序很重要：workspace 写入结束之前不能启动依赖它的读取，第一阶段仍在被搬出单元访问的 UB 也不能直接变成第二阶段的工作区。

## 4. 用一个小例子检查两阶段地址关系

下面把块高缩小到 4，以便直接检查尾行。示例中 M=10，最后一块只有两行；K=7，第二阶段每次组装三列。代码验证输出布局，不模拟设备指令、缓存和同步。

```python
M, K, B, C = 10, 7, 4, 3
groups = (M + B - 1) // B
x = [[r * 100 + c for c in range(K)] for r in range(M)]
scratch = [None] * (groups * K * B)

for g in range(groups):
    for c in range(K):
        for r in range(B):
            if g * B + r < M:
                scratch[(g * K + c) * B + r] = x[g * B + r][c]

output = []
for first_col in range(0, K, C):
    compact = []
    for c in range(first_col, min(first_col + C, K)):
        for g in range(groups):
            for r in range(B):
                if g * B + r < M:
                    compact.append(scratch[(g * K + c) * B + r])
    output.extend(compact)

assert output == [x[r][c] for c in range(K) for r in range(M)]
assert None not in output
```

设备代码可以采用不同的索引生成方式，但必须保持相同的有效元素映射。特别是将最后一块补齐到 64 行后，最终输出行距仍然是 M，不能误用 Mₚ；否则行尾 padding 会逐行累积到输出中。

## 5. 核数和后续重排仍需要实测

下表是结构筛选阶段的本地结果。P54、P55 是内部版本号：P54 使用 32 行中间面板；P55 改为 64 行密集 Gather 面板，省去第一阶段的一部分 UB 组装复制。各行都是该配置一批 30 次调用的统计结果，不是多批独立重复实验。

| 实现 | 工作核数 | 目标用例耗时（μs） |
|---|---:|---:|
| P54：32 行中间面板 | 32 | 652.78 |
| P54：32 行中间面板 | 40 | 717.49 |
| P55：64 行中间面板 | 32 | 645.10 |
| P55：64 行中间面板 | 40 | 694.69 |

32 核和 40 核处理 125 个矩阵时，最忙的核都需要处理四个矩阵。增加核数没有减少这个上限，却改变了并发访问和 workspace 总量。记录支持在这些配置中选择 32 核，但没有单独分离出缓存竞争和其他因素各自的影响。

旧的直接写回路径在此前一次正常包测量中为 879.676 μs。后续多个采用新布局的正常包，目标用例约为 643–646 μs。这是开发不同阶段的结果，能够说明改进的量级，但不能拿跨阶段最低值相除，作为严格的成对加速比。

一些看似能进一步减少工作的修改没有获益：

| 后续改动 | 目标用例耗时（μs） | 观察 |
|---|---:|---|
| 去掉 GatherMask，改用逐行写回 | 726.34 | 去除了压紧步骤，写回组织也随之改变 |
| 融合末阶段 Gather，并增加双输入 | 681.72 | 新增索引与向量工作，没有降低完整耗时 |
| 保留 Gatherb 和 GatherMask，增加双输入 | 655.49 | 同时调整了列块大小，没有形成收益 |

这些结果不能只归结为某一条指令快或慢。GatherMask 在当前路径中承担去填充和生成连续输出的工作，删除它之后必须由其他步骤完成相同任务。

最后的正常包五例本地结果为 5.18、12.05、121.70、116.17、643.16 μs，合计 898.26 μs，五例均通过正确性检查。该包还包含其他输入分支的调整，因此完整总和的改善不能全部归因于本文的目标路径；也没有据此宣称新的赛事平台成绩。

## 6. 什么时候值得增加一份中间布局

这条实现适合考虑中间布局的原因，是输入和输出的连续方向不同，原路径的写回片段较短，而同一批数据可以在局部重排后拼成较长输出。临时区只保存一个核当前处理的矩阵，大小与复用周期都能控制。

迁移到其他转置或重排算子时，先写出两次搬运的实际连续长度，再计算临时区、索引和 UB 的代价。如果原路径已经能够长块读写，再增加一次中转就未必有价值；如果必须让多个核共同写入并消费同一面板，还需要重新安排跨核同步与任务所有权。

最终应比较的是整个调用：新增重排和临时区访问，是否被更好的读写组织抵消。这个案例中的改善来自两端布局和调度共同变化，不能抽象成“多经过一次 L2 就会更快”。
