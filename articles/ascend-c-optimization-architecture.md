# Ascend C 极限调优：从 IndexAdd 看实现方案的切换

本文整理自参与[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)期间的 IndexAdd 开发记录。该赛题要求使用 Ascend C 实现按索引累加：输入 `self`、`source`、一维 `index` 和轴 `dim`，将 `source` 中各切片累加到 `self` 的对应位置，返回与 `self` 同形状的结果。重复索引对应的更新都需要保留，语义对应默认 `alpha=1` 的 [`torch.index_add`](https://docs.pytorch.org/docs/2.12/generated/torch.index_add.html)。

我们在 Ascend 910B4、CANN 8.5.0 上尝试过不同的任务划分、索引计划和数据布局。到后期，仅调整 tile 大小已经很难获得明显改善，工作逐渐转向另一个问题：当前实现规定的数据访问方式，是否限制了后续优化？

本文选取 FP32 路径的一次调整展开。它先经历了一次明确退化，再通过缓冲区复用获得局部收益。这个过程比较适合讨论更换实现方案的成本，以及何时值得继续修改一个暂时更慢的新方案。

## 1. 从更新方向看可选的实现

将目标输入写成二维形式，`self` 为 `[H, A]`，`source` 为 `[H, N]`，沿第二维累加。单行的计算关系是：

```text
Y[r, :] = self[r, :]
按 j = 0, 1, ..., N-1 的顺序执行：
    Y[r, index[j]] += source[r, j]
```

按 source 划分工作很直接：每个核连续读取一段源数据，再更新目标位置。困难在于多个源位置可能指向同一输出。如果不同核同时更新它，就要解决写入冲突；对浮点数据，还要检查更新顺序变化带来的舍入差异。

另一种组织方式是让每个核负责互不重叠的输出行，先为每个目标列构造来源列表，再依次取数累加。例如：

```text
index = [2, 0, 2, 1, 0, 2]

目标列 0 的来源位置：[1, 4]
目标列 1 的来源位置：[3]
目标列 2 的来源位置：[0, 2, 5]
```

列表按源位置递增排列，每一行可以使用同一份计划。计算时同时处理各列的第一次更新，再处理第二次、第三次更新；没有对应来源的列跳过。这样可以在不同输出元素之间并行，同时保留单个输出元素的来源顺序。

这两种方案改变了分核对象、索引访问和输出所有权，属于不同的实现结构。调整其中一条路径的 tile 长度，则仍然是在同一结构内选择参数。

| 组织方式 | 主要收益来源 | 需要付出的成本 |
|---|---|---|
| 按源位置划分更新 | 源数据容易连续读取 | 重复索引的输出冲突，以及合并顺序 |
| 按输出行计算，使用有序来源计划 | 各核输出互不重叠，来源计划可跨行复用 | 建表、离散取数和计划存储 |
| 源数据分块转置后按块取数 | 将多行的同一来源位置合成连续数据块 | 转置、源分块及新的缓冲区安排 |

表中没有一个方案对所有输入都占优。输出行很少时，按行分核可能无法提供足够并行度；来源计划很深时，计划本身又可能占掉过多 UB。决定切换路径的条件，需要包括这些实际约束。

## 2. 保留累加顺序，仍有布局调整的空间

在这条浮点路径中，我们选择保留参考实现的逐来源累加顺序，并使用定向检查验证舍入结果。这样做限制了直接把重复索引改成树形归约的空间，但没有限制不同输出元素之间的调度。

例如，可以按更新次数对目标列排序，让同一层仍需更新的列形成连续前缀，减少后几层的无效计算；计算完成后再恢复列顺序。只要每一列内部的来源列表不变，列之间的重排就不会改变该列的加法顺序。我们原有的 FP32 路径使用了这种组织方式。

下面的 Python 片段只验证“改变列处理顺序，保留列内更新顺序”这一点。用每次加法后转回 FP32 的方式模拟逐次舍入，无需 NPU：

```python
import struct

def fp32(x):
    return struct.unpack("f", struct.pack("f", x))[0]

index = [2, 0, 2, 1, 0, 2]
source = [16777216.0, 3.0, 1.0, 7.0, -2.0, -16777216.0]
self_row = [0.0, 0.0, 0.0]

reference = self_row.copy()
for j, col in enumerate(index):
    reference[col] = fp32(reference[col] + source[j])

positions = [[j for j, col in enumerate(index) if col == c]
             for c in range(len(self_row))]
order = sorted(range(len(self_row)), key=lambda c: -len(positions[c]))
result = self_row.copy()
for level in range(max(map(len, positions))):
    for col in order:
        if level < len(positions[col]):
            j = positions[col][level]
            result[col] = fp32(result[col] + source[j])

assert result == reference == [1.0, 7.0, 0.0]
```

第三列中的大数抵消是有意安排的。若先把 `16777216` 与 `-16777216` 相加，再加 `1`，结果会变成 `1`。因此，减少加法层数前要先确认允许怎样的误差和计算顺序；这里只验证上述有序方案，不讨论任意归约次序的等价性。

## 3. 把逐元素取数改成多行成块取数

本文分析的本地目标输入为 FP32：`self=[2376,655]`、`source=[2376,4960]`、`index=[4960]`，`dim=1`。2376 行共享同一组索引。

原路径保留行优先的源布局，通过展开到多行的索引计划执行 Gather，再逐层 Add。新方案尝试一次处理 8 行，将每个源分块从 `[8,C]` 转成 `[C,8]`。对应的元素偏移是：

```text
转置前：source_tile[r*C + j]
转置后：transposed[j*8 + r]
```

转置完成后，同一源位置在 8 行中的 FP32 数值连续占据 32 字节，代码可以使用 Gatherb 按块取数。结果累加器也采用相应布局，处理完全部源分块后才恢复行布局并写回。

这里调整了源数据的表示方式：索引计划不再为这 8 行分别展开同一个源位置，而是指向一个包含 8 个值的数据块。实现使用 `TransDataTo5HD` 完成局部转置。转置本身增加了工作，是否合算要看后续计划访问与取数节省的成本。

源分块也必须按原顺序处理。块内保留来源位置顺序，块间依次处理，累加器在所有块之间驻留。这个版本没有把转置后的源数据写入 GM；GM workspace 用于索引计划，源数据重排留在 UB 内。

## 4. 新方案的第一次结果明显更慢

下表中的 P135 是当时的基线，P139 是上述八行分块方案的初版，两者都是内部版本号。数据来自同卡交替运行的目标用例，单位为 μs。

| 完整调用 | 第一轮 | 第二轮 |
|---|---:|---:|
| P135：有序计划与逐元素 Gather | 163.523 | 164.114 |
| P139：八行转置与按块取数 | 191.024 | 191.194 |

P139 通过了针对性正确性检查，但两次计时都明显退化。记录中的部分搬运计数下降了，完整延迟却上升。这些计数可能包含等待，也允许不同流水重叠，无法把下降值相加，当作新方案应有的收益。

继续检查布局时发现，源分块上限被设为 1536 个位置，4960 个位置需要处理四块。raw 源缓冲、转置结果、Gather 结果、累加器和常驻计划分别占用空间，其中有些缓冲的有效期并不重叠。

这给出了继续修改的具体理由：能够指出哪块内存在什么时候不再使用，以及复用后会改变哪一项工作量。单凭“按块取数应该更快”，不足以支撑继续投入。

## 5. 复用转置前的缓冲区，四个源块变成两个

源分块转置结束后，后续 Gatherb 读取的是转置结果，raw 不再保存需要使用的数据。修订版把 raw 的低地址部分用于 Gather 结果，高地址部分用于该源块的常驻索引计划；计划搬入也推迟到转置完成之后。

```text
源搬入阶段：raw = 8 行源数据
转置阶段：  raw → transposed
累加阶段：  raw = Gather 结果区 | 常驻索引计划区
            transposed 与 acc 保持独立
下一源块：  等待本块计算完成，再覆盖 raw
```

这份布局有明确的容量条件。设补齐后的目标列数为 Aₚ，源分块长度为 C，该块最大重复次数为 d，则 raw 内的两块区域需要满足：

```text
Gather 结果：8 × Aₚ × 4 字节
索引计划：  d × Aₚ × 4 字节
两者之和 ≤ raw 容量 8 × C × 4 字节
```

此外，建表阶段有自己的空间检查。实际重复次数不满足条件时，代码回退原路径；不能只按平均重复次数安排内存。

修改后，这个输入的 C 从 1536 增大到 2560，源分块由四个减少到两个。计算阶段的布局为：

| 区域 | 字节数 |
|---|---:|
| raw，后续复用为取数结果和计划 | 81920 |
| transposed，包含一个零数据块 | 81952 |
| acc，8 行、补齐至 656 列 | 20992 |
| 合计 | 184864 |

184864 B 是该输入计算阶段的布局大小。源码统一申请的 UB arena 为 190016 B，其他阶段也使用这块空间，两者不要混为一谈。跨阶段复用依赖代码中的同步，单纯让两个指针指向同一地址并不能建立安全的先后关系。

修订版记为 P151。在通过逐位专项后，我们才追加完整五例对照。每例沿用原测试扩展的 30 轮调用，排除辅助 Mul 的计时记录，按原顺序取第 11 至 30 轮，保留原统计脚本的整数转换和中位数计算。以下各行均来自一个完整版本的一次完整运行。

| 运行顺序 | 版本 | 目标 FP32 用例（μs） | 五例合计（μs） |
|---|---|---:|---:|
| A1 | P135 | 166.504 | 668.384500 |
| B1 | P151 | 149.023 | 650.883499 |
| A2 | P135 | 157.143 | 658.722499 |
| B2 | P151 | 149.203 | 649.042500 |

两次完整对照都观察到了改善，随后通过了 156 项完整检查和 153 项发布回归。目标用例的收益在两轮中分别约为 10.5% 和 5.1%；基线本身有波动，不能只选较大的一个比例作为统一加速比。

这组实验支持采用 P151 的整体修改。它同时改变了缓冲区布局、计划搬入时机和分块大小，没有单独测出每项修改的贡献；其他未改路径也有小幅波动，因此不能将五例总和的全部下降都归因于源分块减少。

## 6. 更换实现前，先列出要消除和要新增的工作

这段开发过程里，值得保留的判断顺序是：先检查数值语义允许怎样重排，再比较任务所有权和数据布局，最后为选定结构安排 UB 与流水。每次换方案，都应能够说明原来的哪部分成本会消失，以及增加了哪些成本。

以本文方案为例，收益假设来自多行共享索引、按块取数和减少源分块；新增成本包括转置、计划构建和阶段同步。若换到输出行很少、重复索引很集中，或计划空间超出预算的输入，这些关系就会改变。因此，结构切换需要保留准入条件和回退路径。

还要检查局部收益离完整目标有多远。在 P151 的两次完整结果中，整数用例仍约为 397 μs，除目标 FP32 用例外的其余四例合计约为 500–502 μs。若希望五例低于 600 μs，而其他路径保持当前耗时，目标 FP32 用例就需要降到约 98–100 μs。只继续优化这条已到约 149 μs 的路径，仍有很大距离；下一轮应重新比较各路径的可优化成本。

所谓接近极限，在本文中是指现有结构的常规调整已难以推进。我们没有测得硬件性能下界，也没有证据证明算子已经达到设备极限。新结构让一些原本固定的成本变成可调整项，但同样需要经过正确性、资源布局和完整计时的检验。

文中数据来自 2026 年 9 月保存的本地实验，不是新增赛事平台成绩；输入形状已列出，完整输入值和工程未随文提供，因此这些数值用于分析该轮设计取舍。本文整理期间未新增 NPU 实验。AI 参与了代码实现、实验分析和文章整理。
