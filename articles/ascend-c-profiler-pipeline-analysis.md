# Ascend C 性能分析：Vector 时间降了，算子为什么没变快

在一次 IndexAdd 优化中，我们把 `aiv_vec_time` 从 110.591 μs 降到了 36.016 μs，下降约 67%。但同轮测试中，算子的 `Task Duration` 从 396.4275 μs 变为 397.6680 μs，没有出现预期的提速。

这个案例来自[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)的 IndexAdd 赛题。任务以 `self` 为初值，将 `source` 沿指定轴的切片累加到 `index` 指定的位置，重复索引会更新同一输出。实验环境为 Ascend 910B4、CANN 8.5.0，本文使用本地构造的 INT32 输入：

```text
self   : [23, 12, 102, 26]
source : [23, 1200, 102, 26]
index  : [1200]
dim    : 1
```

连续内层共有 `102×26=2652` 个元素，每行 10608 B，相邻行起点并非都满足 32 字节对齐。两个版本都保留 INT32 原子累加，优化集中在源数据对齐和核内流水。下面讨论这次实验能够解释什么，以及哪些结论还不能从计数器中直接得到。

## 1. 先把总耗时和流水计数放在同一张表里

基线在项目内记为 P135，改造版本记为 P150。每个版本采集 30 次目标调用，舍弃前 10 次，取后 20 次的中位数。下表来自同轮原始 `op_summary`，不是将不同阶段的最低值拼在一起：

| 指标 / μs | P135 基线 | P150 改造后 | 变化 |
|---|---:|---:|---:|
| Task Duration | 396.4275 | 397.6680 | +1.2405 |
| aiv_vec_time | 110.5910 | 36.0160 | -74.5750 |
| aiv_scalar_time | 67.6145 | 47.2280 | -20.3865 |
| aiv_mte2_time | 369.8635 | 385.9425 | +16.0790 |
| aiv_mte3_time | 296.9120 | 287.2135 | -9.6985 |

如果只展示 Vector 一行，这会是一项十分显眼的改进；加入 Task Duration 后，结论就需要收紧：改造显著改变了流水计数，但这一轮没有观察到算子总耗时收益。

由于只有一组基线与候选对照，不能把 1.2405 μs 的差值写成已经确认的稳定回退。这个版本没有因此产生新的完整五例发布结果，也没有对应的官方成绩。对当时的工程决策来说，现有收益证据不足，继续沿用基线即可。

## 2. 各条流水的时间不是串行账单

`aiv_vec_time`、`aiv_mte2_time` 和 `aiv_mte3_time` 分别反映不同执行单元上的指令时间。[CANN PipeUtilization 文档](https://www.hiascend.com/document/detail/en/canncommercial/850/devaids/optool/atlasopdev_16_0099.html)给出了对应的计数口径；它们与一次任务从开始到结束的持续时间不是同一个量。

把基线的 Vector、Scalar、MTE2、MTE3 相加，结果约为 845 μs，已经超过 396 μs 的任务持续时间。这些列显然不能当作首尾相接的四段耗时。不同流水可以重叠，汇总指标也不等于同一条串行执行轨迹。

一个简化的三级流水可以说明问题。假设每块搬入需要 10 个时间单位、计算需要 3 个、搬出需要 8 个，且缓冲和依赖允许三者充分重叠，那么进入稳态后，吞吐间隔主要由最慢的搬入阶段决定。把计算从 3 减到 1，会缩短计算阶段，却未必改变每隔 10 个单位完成一块的节奏。

这个例子只解释重叠，不是对 P150 设备时间线的复原。真实 Kernel 还有初始化、预取、同步、原子写回和尾块。判断某段优化能否缩短总耗时，需要知道它位于哪条限制整体完成时间的依赖路径上。

因此，不能从基线总耗时中直接减去省下的 74.575 μs，预测新版本应降到约 322 μs。也不能把其余几列的增减相加，用来“对平”剩余误差。这种算账忽略了流水之间的重叠关系。

## 3. 新流水省下了什么，又付出了什么

P135 将多条 source 行连续搬入 UB，对不对齐的行通过 Gather 整理后再原子写回。某些写回直接读取输入缓冲，因此输入槽重新装填前，要等待相应 MTE3 读取完成。

P150 将两组输入缓冲和两组对齐输出缓冲分开。输入先通过 UB 内复制或 GatherMask 整理到输出缓冲；整理结束后，MTE2 就可以复用输入槽，MTE3 则继续读取独立的输出槽。

这一安排改变了缓冲复用的依赖：

```text
输入槽可以复用：本槽的 Vector 对齐处理已经结束
输出槽可以复用：本槽的 MTE3 原子写回已经结束
```

它同时用掩码整理替换了原路径中的部分 Gather 工作。这与 Vector 计时明显下降的现象相符。不过，指标变化不能证明所有收益都来自某一条替换指令，因为缓冲、同步和批量大小也一起发生了变化。

额外输出存储占用了 UB。目标形状下，基线每批读取 6 行、63648 B；P150 每批读取 4 行、42432 B，显式 UB 使用量为 177984 B。批量缩小意味着同样的 source 行数需要更多批次，也改变了指令下发和预取节奏。

这是一项具体代价，而不只是笼统的“同步有开销”。独立输出槽给输入复用创造了机会，同时减少了每次连续搬入的数据量。最终是否有利，要由整条流水的运行结果决定。

表中 MTE2 时间增加与这个代价存在可能的联系，但本次实验没有单独固定批量大小来隔离变量，不能断言增加的 16.079 μs 全由批量缩小造成。可以确认的是布局和批量确实变化，不能确认的是每项变化各自贡献了多少时间。

## 4. MTE2 时间接近总耗时，仍不足以证明带宽到顶

P150 的 MTE2 时间约 386 μs，与约 398 μs 的任务时间接近。它提示搬入路径值得优先检查，但“搬入在当前实现中占据较长时间”与“设备内存带宽已达到极限”之间，还差一组证据。

任务时间和流水时间描述的是执行过程。若要判断带宽利用率，还需要明确数据量来自哪里：是算法要求的有效输入字节数、实际总线传输量，还是工具统计的某一级缓存访问量。三者不能互换。

本例 source 包含 `23×1200×2652` 个 INT32 元素，即 292780800 B。用这个数除以 P150 总耗时，可以算出约 736 GB/s 的“源数据有效处理率”。但这个值没有计入 self 初始化、索引搬运和输出更新，也没有区分源数据来自 DDR 还是缓存，因此不能直接当成实测 DDR 带宽，更不能与规格峰值直接比较后宣布饱和。

做对照实验时，同样要保留影响访存的条件：工作集大小、核数、搬运粒度、缓存策略，以及目标调用之前运行了什么。把 IndexAdd 换成简单读入或 ReduceSum 可以帮助定位，但它们的归约、写回和调度成本不同。某个参考算子更慢，不能反向证明当前实现已经没有优化空间。

有关等待和阻塞，还应查看所用采集模式是否提供更细的指标。PipeUtilization 文档单独列出了 Scalar wait、指令队列阻塞等字段；未采集这些数据时，不能把一个较大的汇总时间直接解释成某种特定等待。

## 5. 下一轮实验应该区分哪些解释

这组记录已经足够否定“Vector 下降多少，总耗时就下降多少”的预测，却还不足以唯一确定 P150 没有变快的原因。下一轮若继续投入，实验应围绕不同解释来设计。

| 待验证的解释 | 可采用的对照方式 | 重点观察 |
|---|---|---|
| 批量从 6 行降到 4 行抵消了收益 | 在可实现的共同批量下比较两种缓冲组织 | 总耗时与 MTE2 时间是否同向变化 |
| 原子写回及其依赖仍限制吞吐 | 用明确标注的诊断路径分离搬入、对齐和写回 | 哪个阶段使重叠机会消失 |
| 部分核的尾部决定完成时间 | 采集核级数据，核对每核任务量与尾批 | 最晚结束的核是否明显偏离平均水平 |

诊断路径可能临时省略某项工作，因而不能替代完整算子的正确性或性能结果。它的用途是检验一个原因是否成立。原因缩小后，再回到保留全部语义的实现验证收益。

对 P150，本轮应保留的结论是：输入与输出缓冲分离、改用掩码对齐后，Vector 和 Scalar 计时下降；与此同时，批量缩小、MTE2 时间增加，目标输入总耗时没有改善。下一次值得投入的方向，是搬入粒度与依赖关系，而不是继续追求更小的 Vector 数字。
