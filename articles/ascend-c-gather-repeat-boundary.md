# Ascend C 边界排错：扩大分块后的一次 Gather 重复次数截断

扩大 Tiling 分块时，通常先检查 UB 是否放得下、搬运地址是否对齐。然而，即使这些条件都成立，某条 API 调用也可能已经超过内部参数能够表达的范围。

本文复盘[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)中 Greater 算子的一次排错。任务对两个广播输入执行逐元素 `x > y`。目标输入为 INT32，形状是 `[336,1,1023]` 和 `[336,120,1023]`，开发环境为 Ascend 910B 系列设备、CANN 8.5.0。

一个扩大分块的版本在本地设备检查中产生了 483349 个错误输出。地址模型和 UB 预算检查都通过，最终原因藏在所用 SDK 的 Gather 按元素数接口中：内部将重复次数保存为 `uint8_t`，304 次被截成了 48 次。

## 1. 这次扩块原本想省掉什么

在这一形状下，每条 1023 元素的共享行要与另一侧的 120 行比较。实现可以先在 UB 中准备周期重复的数据，然后让连续搬入的密集输入与它逐块比较，减少反复构造广播数据的次数。

问题版本在项目中记为 P18。它将缓冲容量扩大到 19456 个 INT32 元素，按 64 元素对齐后的行距为 1024，因此一个计算块安排 19 行，有效数据量为：

```text
缓冲容量 CAP = 19456
对齐后的行距 = 1024
每块行数 = 19456 / 1024 = 19
每块有效元素数 = 19 × 1023 = 19437
```

准备广播数据时有两条路径。如果当前地址恰好位于共享行的起点，就重复复制对齐行，再用 `GatherMask` 去掉填充；如果起点处于行内，则先生成周期索引，再调用 `Gather` 收集数据。

这里的 `Gather` 和 `GatherMask` 是不同接口。实际发生截断的是非零起始相位下的 `Gather` 调用，不能因为名字相近，就把两条路径按相同约束分析。

## 2. 32 位 count，并不代表内部重复次数也是 32 位

出问题的调用非常短：

```cpp
Gather(packed, row, index, uint32_t(0), CAP);
```

`CAP` 为 19456，外层 `count` 参数为 `uint32_t`。从调用点看，这个数既没有超过整型范围，也没有超过已经分配的目标缓冲。

但检查当时归档的 CANN 8.5 SDK 头文件后，可以看到该架构分支把按元素数调用拆成完整 repeat 和尾部两部分，关键代码为：

```cpp
const uint32_t elementCountTail = count % elementCountSingleRepeat;
const uint8_t repeatTime = count / elementCountSingleRepeat;
```

对本例的 32 位数据，`elementCountSingleRepeat` 为 64，于是：

```text
19456 / 64 = 304
304 转为 uint8_t = 48
实际完整重复覆盖 = 48 × 64 = 3072 个元素
19456 % 64 = 0，没有尾部调用
```

[Gather 官方接口说明](https://www.hiascend.com/document/detail/en/canncommercial/800/apiref/ascendcopapi/atlasascendc_api_07_0092.html)列出了高维切分接口的 `uint8_t repeatTimes` 及其取值范围。这里进一步确认的是：当时使用的按元素数封装，也在内部走到了这个窄参数。

这一结论有版本和架构边界。归档头文件对部分架构直接调用另一套实现，不能把本例写成所有产品、所有版本的 Gather 都存在同一限制。移植或升级后，应重新核对实际编译命中的分支。

## 3. 为什么它只造成一部分结果错误

被漏写的目标区域没有立刻触发访问异常。`packed` 先前被用于生成周期索引的临时计算，其中仍保留着商乘以行宽的中间值。Gather 只覆盖前 3072 项，后面的中间值就被误当作广播输入参与了比较。

这也解释了为什么错误数量远小于输出元素总数。

首先，只有非零起始相位会进入这条 Gather 路径。P18 按连续区间分核，本例用了 40 个核，每核区间上限为 1031680 个输出元素。核间起点满足输出对齐要求，却不一定是 1023 的倍数。例如第二个核的起始相位为：

```text
1031680 % 1023 = 496
```

其次，跨入下一个 batch 后，起点恢复到共享行边界，会改走另一条准备路径。因此，缺陷主要作用于相关核的第一个 batch 片段。

最后，布尔比较会掩盖部分输入错误。错误的广播值与正确值即使不同，与另一侧数值比较后，也可能碰巧得到相同的真假结果。漏写了多少项，不能直接换算成多少个错误输出。

当时的 CPU 因果模型按相同随机种子生成输入，复现分核、相位、残留工作值和比较过程，预测错误数量为 483349，与设备记录一致。原设备产物只保存了错误总数，没有完整错误位置，所以这里能确认的是数量吻合，不能宣称逐位置复现已经完成。

## 4. 修复保留外层分块，只拆开 Gather 调用

修复版本记为 P21。它保持原分核、缓冲容量和比较逻辑，仅把一次 Gather 改成三次：

```cpp
for (uint32_t base = 0; base < CAP; base += 8192) {
    const uint32_t n = CAP - base < 8192 ? CAP - base : 8192;
    Gather(packed[base], row, index[base], uint32_t(0), n);
}
```

三段长度为 8192、8192、3072，对应 128、128、48 次 repeat。目的位置和索引张量一起向后移动，源 `row` 保持不变，因为索引中已经保存了相对该行的字节偏移。

这里不能只移动目标起点。如果第二次调用仍从 `index[0]` 读取索引，就会重新收集第一段的广播模式；这种错误也可能只在某些行宽或相位下暴露。也不应再给源地址叠加 `base`，否则会把已经编码在索引里的位移重复计算。

8192 是本次修复采用的分段长度，不是宣称该 API 的最大合法长度。选择它是为了让每次调用保持在 128 次 repeat，并与已有索引生成分段一致。缓冲容量、一次计算处理量和一次 API 调用处理量，可以分别设置。

下面的独立模型同时检查窄化和修复后的周期索引，不需要设备：

```python
cap, k, phase = 19456, 1023, 496
requested = cap // 64
assert requested == 304
assert (requested & 0xff) * 64 == 3072

row = list(range(k))
offsets = [((phase + i) % k) * 4 for i in range(cap)]
fixed = [None] * cap
chunks = []
for base in range(0, cap, 8192):
    n = min(8192, cap - base)
    assert n % 64 == 0 and n // 64 <= 255
    chunks.append(n)
    for j in range(n):
        fixed[base + j] = row[offsets[base + j] // 4]

assert chunks == [8192, 8192, 3072]
assert fixed == [row[(phase + i) % k] for i in range(cap)]
print("split Gather model passed")
```

## 5. 正确性修复成立，扩块方案仍然没有胜出

P21 在同一目标输入上通过了设备逐位比较，错误数量归零。结合源码仅拆分 Gather 的差异，以及 CPU 对旧版错误数量的预测，重复次数截断得到了较充分的验证。

性能结果则是另一件事。下面是修复版与当时基线的同场夹测，三组均取 30 次目标调用中后 20 次的中位数：

| 运行顺序 | 耗时 / μs |
|---|---:|
| 前置基线 | 275.0155 |
| P21，修复后的宽分块 | 289.1300 |
| 后置基线 | 275.2550 |

修复版比两端基线均值慢约 14 μs，因此没有作为性能改进采用。没有把错误版本的计时拿来宣称加速，也没有把正确性恢复等同于优化成功。这些都是本地构造输入的历史结果，不代表官方成绩。

## 6. 扩大 Tiling 时，把参数上限列入推导

这个缺陷漏过了 UB 容量、分核覆盖和周期索引的 CPU 检查，因为那些检查默认 Gather 会处理完整的 `count`。它们验证了地址关系，却没有验证调用实际能表达的处理长度。

此后再扩大分块，除了重算存储预算，还应顺着调用链检查：元素数怎样换算成 repeat，repeat 保存为什么类型，完整重复与尾部怎样衔接。针对这类封装，边界测试应覆盖重复次数到达 255、跨到 256，以及存在尾部元素的情况，而不只测试原容量和新容量两个点。

定位时也可以利用失败范围缩小问题：若地址分布看起来正确，某些相位失败、另一些相位通过，就先比较两条执行路径；若一大段数据保留了规律性的旧值，就检查写入覆盖，而不是立即归因于随机同步错误。本例中，沿着“哪些元素没有被 Gather 写入”追查，比继续调整广播公式更接近原因。
