# Ascend C Greater 实现：用 Min/Max 与 EQ 完成精确的 INT32 比较

本文讨论的案例来自[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)的 Greater 赛题。任务是对两个支持广播的输入逐元素执行 `x > y`，输出布尔结果。我们使用 Ascend 910B 系列设备、CANN 8.5.0 开发，其中一组本地性能输入为 INT32，形状分别是 `[336,1,1023]` 和 `[336,120,1023]`，输出包含 41,247,360 个元素。

这一实现有两个问题需要同时处理：共享的一行怎样高效广播，以及 INT32 的大小关系怎样在向量路径上保持精确。本文重点讨论后者。最终代码里虽然出现了 `half` 和 `Cast`，参与大小比较的输入却始终保留为 INT32。理解这条界线，才能判断哪些转换可以压缩，哪些转换会改变结果。

## 1. 不能把 INT32 输入直接交给浮点比较

选择比较指令时，需要同时看数据类型和比较模式。`Compare` 存在 `GT` 枚举，不代表每种类型都支持它。[官方 Compare 文档](https://www.hiascend.com/doc_center/source/zh/CANNCommunityEdition/910beta2/API/ascendcopapi/atlasascendc_api_07_0066.html)按产品列出了能力差异：Atlas A2 路径的 INT32 支持 `EQ`。本文 CANN 8.5 实现也采用 INT32 等值比较，再组合其他整数操作完成 Greater。

一种容易想到的替代办法，是把两个 INT32 输入转为 FP32，再执行浮点 `GT`。这对小整数可行，对完整 INT32 值域不成立。例如，16,777,217 和 16,777,216 是不同整数，转换为 FP32 后却可能成为同一个数。原本为真的大于关系随之消失。

下面的例子只依赖 Python 标准库，可以直接验证这个问题：

```python
import struct

def fp32(x):
    return struct.unpack("<f", struct.pack("<f", x))[0]

x, y = 2**24 + 1, 2**24
assert x > y
assert fp32(x) == fp32(y)
print(x > y, fp32(x) > fp32(y))  # True False
```

改成 `x - y > 0` 同样需要小心。两个合法的 INT32 输入，其差值未必能由 INT32 表示；例如最大正整数减去 -1 就会越界。在 C++ 标量代码里，带符号溢出还涉及未定义行为。没有范围证明时，不能用一次减法替代完整值域的有序比较。

## 2. 用整数最值把大小关系变成等值关系

对有符号整数，有两条直接可用的等价关系：

```text
min(x, y) == x  ⇔  x <= y
max(x, y) == y  ⇔  x <= y
```

将等值判断的结果反转，就得到 `x > y`。最值操作只选择一个输入，不需要计算可能溢出的差值，也不需要压缩输入的有效位。

两条式子在数学上表达同一个条件，在 Kernel 中却各有用途。广播实现通常把共享输入整理到 `packed` 缓冲，将另一侧连续搬入 `dense` 缓冲。共享输入既可能在左，也可能在右：

| 共享输入的位置 | `packed` 保存 | `dense` 保存 | 覆盖 `dense` 后执行的等值判断 |
|---|---|---|---|
| 左操作数 | x | y | `min(x,y) == x` |
| 右操作数 | y | x | `max(x,y) == y` |

这样，两个方向都可以覆盖 `dense`，保留 `packed` 作为等值比较的另一个输入。缓冲区不必再增加一份完整的最值结果。

冻结实现的核心代码如下。`dense`、`packed` 均为 INT32，`mask` 保存比较位图；`na` 为已经满足计算对齐要求的元素数。片段省略了搬运、队列和外围同步，不能单独作为完整 Kernel 使用。

```cpp
if (sharedLeft) {
    Min(dense, packed, dense, na);
} else {
    Max(dense, dense, packed, na);
}
Compare(mask, dense, packed, CMPMODE::EQ, na);
```

这里最容易写错的是右操作数广播时的方向。如果仍然执行 `Min`，再与共享的右操作数比较，得到的就不再是 `x <= y`。形状广播是对称的，Greater 的操作数顺序不是。

## 3. 比较结束后，才把结果压缩到 half 和字节

`Compare` 生成的是位图，而输出需要逐元素的布尔值。当前位图表示 `x <= y`，所以位为 1 时选择 0，位为 0 时选择 1，随后转换成逐字节的 0/1。

这一阶段使用 half 保存中间结果没有精度问题，因为此时只剩下 0 和 1。它与“先将 INT32 输入转换为 half”发生在完全不同的位置：前者编码已经确定的判断结果，后者会在判断之前丢失输入信息。

在后续的紧凑版本中，`packed` 完成最后一次等值比较后，就不再需要保存本块的原始整数。代码在确认 Vector 读取结束后，将这片存储重新解释为 half，交给 `Select` 写入 0/1，再通过 `Cast` 写入字节输出。

`ReinterpretCast<half>()` 本身没有把整数数值转换成 half。它只是建立另一种类型的存储视图；有意义的 half 数据由后续 `Select` 重新写入。若在比较结束前覆盖这片区域，或者把原 INT32 的位模式直接当作 half 数值使用，都会破坏这套逻辑。

这项复用也有明确边界：本实现会为下一块重新准备 `packed`。如果另一套实现打算让广播结果跨多个计算块常驻，就不能在第一个块比较完成后覆盖它。能否复用，应由最后一次读取发生在哪里决定。

## 4. 定向测试要覆盖相等、相邻大整数和两个方向

随机输入可以发现错误，但不一定能解释错误。对这条等价改写，至少应专门覆盖三类值：相等的输入、超过 FP32 连续整数表示范围的相邻值，以及 INT32 的正负极值。

下面的 CPU 模型验证两条等价关系，不模拟 Ascend C 指令和同步：

```python
values = [
    -(2**31), -(2**31) + 1,
    -(2**24) - 1, -(2**24),
    -1, 0, 1,
    2**24, 2**24 + 1,
    2**31 - 2, 2**31 - 1,
]

for x in values:
    for y in values:
        left_shared = not (min(x, y) == x)
        right_shared = not (max(x, y) == y)
        assert left_shared == (x > y)
        assert right_shared == (x > y)
print("121 pairs passed")
```

设备验证还要补上广播地址和存储边界。对于 `[B,1,K]` 与 `[B,M,K]`，交换两个输入后，应重新验证相同形状关系下的反向比较；分块跨过 batch 边界时，应切换到下一条共享行；尾块只写有效的字节数，不能把计算用的对齐补齐区写进输出。

本项目为紧凑版本保留了 28 项定向 row 检查，覆盖两个操作数方向、极值和不规则形状，其中同时包含专用分支和回退分支；同一安装包也完成了五例逐位正确性验证。这些检查用于验证具体实现；整数恒等式成立，并不能代替地址、同步和尾部处理的测试。

## 5. 精确比较确定以后，再压缩周边开销

这条 Min/Max 加 EQ 的比较路径已经存在于基线中。后续实验没有再次改变比较语义，而是减少比较结束后的临时存储，将每块容量从 8192 增加到 10240 个元素。

为便于对应记录，下表将原基线记为 F04，紧凑存储版本记为 P33；这些只是项目内部版本号。P33 保留双输入槽、连续输入搬运和周期 Gather，将常量向量缩至 128 个 half，并复用比较完成后的 `packed` 存储。目标形状下，显式 UB 分配为 187904 B，加预留空间后为 196096 B。

| 同场运行顺序 | Greater 目标输入耗时 / μs |
|---|---:|
| F04，前置基线 | 277.7455 |
| P33，紧凑存储 | 273.0950 |
| F04，后置基线 | 277.4760 |

每组包含 30 次目标调用，剔除前 10 次，按原评测脚本口径取后 20 次的中位数。数据来自本地构造输入上的历史设备实验，不是赛事官方成绩。

P33 在这一轮比两端基线均值少 4.51575 μs，约 1.63%。这组数据支持紧凑实现值得保留，但不能把收益全部归因于某一条指令，也不能据此承诺其他形状具有相同比例的提升。

这个案例中，可优化的空间落在比较结果的表示、缓冲生命周期和分块容量上。输入保持 INT32，比较完成后再收缩结果的存储范围，既保留了精确语义，也给后续调优留下了余地。
