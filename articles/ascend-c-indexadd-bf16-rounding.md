# Ascend C IndexAdd 调优：减少 Cast 之前，先确认 BF16 的舍入位置

本文的案例来自[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)中的 IndexAdd 赛题。输入包括 `self`、`source`、一维 `index` 和累加轴 `dim`，计算以 `self` 为初值，将 `source` 的各个切片加到 `index` 指定的位置。重复索引可能让同一个输出元素被更新很多次。

我们在 Ascend 910B4、CANN 8.5.0 上开发了 BF16 路径。本文使用的本地性能输入为 `self=[12,198,123]`、`source=[12,500,123]`、`index=[500]`，`dim=1`。每次索引更新对应 123 个 BF16 元素，单行有效长度为 246 B，既有重复累加，也有非 32 字节对齐的行宽。

实现中，每次更新都包含类型转换。乍看之下，将整段计算提升到 FP32、最后再转换一次，是很直接的优化方向。但它可能改变参考结果。实际获得收益的版本保留了每次更新后的舍入，将主要改动放在源数据的搬运组织上。

## 1. 三次 Cast 处理的是不同问题

这条路径将累加状态保存为 BF16，计算时转换到 FP32。一次更新的核心片段如下，`dst` 和 `value` 为 BF16，`a` 和 `b` 为 FP32；省略地址和队列处理：

```cpp
Cast(a, dst, RoundMode::CAST_NONE, inner);
Cast(b, value, RoundMode::CAST_NONE, inner);
PipeBarrier<PIPE_V>();
Add(a, a, b, inner);
PipeBarrier<PIPE_V>();
Cast(dst, a, RoundMode::CAST_RINT, inner);
PipeBarrier<PIPE_V>();
```

三次转换不能视为同一类冗余工作。

| 转换 | 作用 | 可以考虑的调整 |
|---|---|---|
| 当前累加值 BF16 → FP32 | 读出上一步已经舍入的状态 | 若改成常驻 FP32，需核对是否仍保留原舍入节点 |
| 当前源值 BF16 → FP32 | 为本次加法准备输入 | 可以尝试批量转换，但会增加存储量 |
| 加法结果 FP32 → BF16 | 形成下一次更新使用的状态 | 延后到循环结束会改变运算过程 |

对普通有限 BF16 数值，提升到 FP32 可以精确表示原值；真正丢弃低位的位置在回写 BF16 时。冻结实现使用 `CAST_RINT`，按最近偶数舍入；CANN 的 [Cast 说明](https://www.hiascend.com/document/detail/zh/canncommercial/83RC1/API/ascendcopapi/atlasascendc_api_07_0072.html)给出了该舍入模式的规则。

这里保留逐次舍入，是根据本项目参考调用和定向测试采用的实现约束，并非宣称所有框架、设备上的 IndexAdd 都采用同一条计算路径。[PyTorch 数值精度说明](https://docs.pytorch.org/docs/2.14/notes/numerical_accuracy.html)也明确指出，数学上相同的计算不保证跨平台、跨版本逐位一致。实现兼容时，需要先确定要对照的具体参考行为。

## 2. FP32 累加到最后一次转换，会改变什么

设一个输出元素初值为 256，接收两次值为 1 的更新。在 BF16 的这一数值区间，相邻可表示值为 256、258。257 恰好处于中点，按最近偶数规则舍入为 256。

```text
每次更新后转回 BF16：
256 + 1 → 257 → 256
256 + 1 → 257 → 256
最终为 256

全程保留 FP32，最后转回 BF16：
256 + 1 + 1 → 258
最终为 258
```

差异在大数抵消时更明显。从零开始，依次加上 `[256,1,-256]`：逐次 BF16 舍入得到 0；FP32 保留中间结果，最后转换得到 1。

后者在这个例子中更接近实数求和结果，但这不足以说明它能替换既定参考实现。算子验证比较的是要求的数值行为，不能只根据中间精度更高来判断兼容性。

下面的独立 Python 例子通过位操作模拟 FP32 到 BF16 的最近偶数舍入，验证上述两个有限数值例子。它没有模拟设备对非正规数和特殊值的全部行为：

```python
import struct

def fp32(x):
    return struct.unpack("<f", struct.pack("<f", x))[0]

def bf16(x):
    bits = struct.unpack("<I", struct.pack("<f", x))[0]
    assert bits & 0x7f800000 != 0x7f800000  # 本例仅处理有限数
    bits = (bits + 0x7fff + ((bits >> 16) & 1)) & 0xffff0000
    return struct.unpack("<f", struct.pack("<I", bits))[0]

def accumulate(initial, updates, round_each):
    acc = bf16(initial)
    for value in updates:
        acc = fp32(acc + bf16(value))
        if round_each:
            acc = bf16(acc)
    return bf16(acc)

assert accumulate(256, [1, 1], True) == 256
assert accumulate(256, [1, 1], False) == 258
assert accumulate(0, [256, 1, -256], True) == 0
assert accumulate(0, [256, 1, -256], False) == 1
```

这两个例子分别隔离了连续小增量和抵消场景。随机输入即使通过，也未必能覆盖这种差异；重复索引测试需要有意安排更新值和顺序。

## 3. 源数据可以批量转换，但容量和无效工作会增加

保留每次加法后的 BF16 舍入，仍可以尝试批量转换源数据。源值不会随着累加更新，提前转换一批源行，不会改变这些有限数值本身。

我们用内部版本 P62 测过这个方向：在一批源数据搬入后一次性转换成 FP32，后续逐条索引更新时读取对应的 FP32 行。累加器仍然每次转回 BF16，没有把舍入推迟到末尾。

这个修改减少了源端 Cast 的调用次数，却需要较大的 FP32 源缓冲。它还可能转换当前核根本不会消费的行：各核负责不同的输出范围，只有索引落在该范围内的源行才需要参与更新。

同卡完整对照中，基线 P58 的两次五例总和为 733.70 / 737.66 μs，P62 为 738.19 / 739.30 μs。目标 BF16 用例分别为基线 41.50 / 41.57 μs、候选 41.73 / 41.13 μs，没有形成稳定改进。

因此，这个候选被放弃。结论限定在这份批量转换实现：减少 API 调用没有抵消容量、转换范围和调度变化的成本，不能推广为“批量 Cast 总是无效”。

## 4. 保留舍入过程，改成连续搬入短源行

另一个版本 P80 沿用了 P58 的累加过程，改动集中在源数据搬入。

原 Load 将一批源行作为多个短 block 搬入 UB，每行补齐到 32 字节。本文行宽为 123 个 BF16 元素，246 B 有效数据对应 256 B 的 UB 行步长。改进版则把这一批源行当成一段连续数据搬入，行间保持紧凑排列。

```text
原 UB 布局： [246 B 数据 | 10 B 填充] [246 B 数据 | 10 B 填充] ...
新 UB 布局： [246 B 数据][246 B 数据][246 B 数据] ...
```

这改变了 DataCopyPad 的 block 组织：从 n 个短 block 变为一个长 block，并不意味着原来一定调用了 n 次搬运 API。读取的有效数据量仍然相同。

紧凑布局带来新的问题：第 j 行的起点为 `j×123×2` 字节，大部分行的起点不满足后续向量操作需要的对齐。P80 先根据索引判断当前核是否需要这一行；需要时，如果行起点未对齐，就用一次短 Gather 将它整理到对齐的临时行缓冲，再执行原来的 Cast、Add 和舍入。

因此，新增 Gather 的范围受到两层限制：只处理当前核负责的更新，只处理未对齐的行。对齐行直接使用已有输入位置。

```text
连续搬入一批源数据
        ↓
按原 index 顺序检查更新
        ↓ 当前核需要这条更新
对齐行直接使用；未对齐行短 Gather
        ↓
原来的 BF16 → FP32 → Add → BF16
```

新增缓冲包括一个对齐源行和一份行内偏移表。这份实现最多增加 3072 B，并结合原路径的 UB 预算限制决定是否适用。它没有为所有源行建立完整的 FP32 副本。

下面是同一轮四批完整运行的结果。第三例为本文 BF16 输入，其余四例用于检查完整版本。每一行都来自一次完整五例运行，没有拼接不同候选的单例最小值。

| 运行顺序 | 版本 | BF16 用例（μs） | 五例合计（μs） |
|---|---|---:|---:|
| A1 | P58 基线 | 41.38 | 736.06 |
| B1 | P80 连续搬入 | 31.26 | 723.65 |
| A2 | P58 基线 | 42.01 | 738.21 |
| B2 | P80 连续搬入 | 31.26 | 725.44 |

两轮目标用例分别减少 10.12 和 10.75 μs，完整版本随后通过了发布回归。其他分支也有计时波动，不能把总和下降的每一微秒都算作这条路径的收益。

P80 的结果说明，在保持原累加顺序和舍入节点的前提下，仍然可以通过搬运布局获得改善。性能修改不一定要从算术指令本身开始。

## 5. 验证用例应覆盖被改变的数值和布局边界

这类优化需要分别验证数值行为与数据位置。只检查最后的误差统计，出现问题后很难判断是舍入变化、漏掉一次重复更新，还是未对齐行取数错误。

我们保留的 BF16 专项包含全重复索引、`[256,1,-256,0.5]` 周期更新、非对齐行宽和源批次尾部。抵消用例检查原更新顺序是否保留；不同列填入不同数值，则有助于发现短 Gather 的偏移错误。

比较规则也要明确。逐位相等、逐元素容差和允许一定错误比例，是不同的要求。本文历史 BF16 专项使用参考结果与容差检查，不能把“全部通过”改写成所有数值逐位一致。若要验证舍入节点是否保留，可以另加可精确计算的定向例子，直接比较预期值。

非有限值应单独分类。NaN、正负 Inf 的对应关系先按算子约定检查，再对有限元素计算误差；不要直接让 `abs(a-b) ≤ rtol×max(abs(a),abs(b))` 覆盖所有值，否则 Inf 参与阈值计算时可能掩盖错误。

当一种优化需要改变累加精度或舍入位置时，应把它作为数值行为变化单独评估。当现有参考行为必须保留时，则可以继续调整批量读取、对齐整理、计划复用和输出分工。把这两类修改分清楚，既能减少无效尝试，也更容易解释一个更快版本为什么仍然正确。
