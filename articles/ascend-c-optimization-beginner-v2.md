# Ascend C 算子优化入门：数据搬运、分核与 Tiling

本文整理自我们参与[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)期间的开发实践。该赛事要求使用 Ascend C 完成指定算子的实现与性能优化。本文涉及的性能评测以通过精度验证为前提，再比较各验证用例的耗时总和，因此实现需要兼顾不同数据类型和 Shape 下的性能。

这里选取其中的 **Concat 赛题** 作为主要案例。题目要求接收一组输入张量和拼接轴 `dim`，将各输入按顺序拼成一个输出张量，语义对应 `torch.cat(inputs, dim)`。各输入在拼接轴上的长度可以不同，其他对应维度保持一致；实现需要保留输入元素的值及排列顺序。

赛题提供的公开调用样例使用一个 `[128, 256]` 的 FP16 张量，沿最后一维随机拆成若干不等长片段，再调用待实现的算子将它们拼回，检查结果是否与原张量一致。分片生成逻辑允许零长度输入。这是公开样例的构造方式，性能测试还需要覆盖其他输入规模、类型和拼接位置。

Concat 的算术工作很少，主要成本在数据搬运。沿第一维拼接时，一路连续输入通常可以整段复制；沿最后一维拼接时，同一路输入在输出中可能被拆成许多短片段。输入路数、单路行宽和拼接轴的位置，都会影响搬运粒度及核间任务划分。下面围绕这些问题讨论分核、UB 分配和流水，实验环境为 Ascend 910B4、CANN 8.5.0。

## 1. 从地址关系确定搬运方式

先将赛题中的多输入拼接简化为两路连续输入，沿最后一维拼接：

```text
A: [M, a]
B: [M, b]
Y: [M, a + b]
```

令 `W = a + b`，并将张量按行展开为一维数组。第 r 行的复制关系为：

```text
A[r*a : (r+1)*a] → Y[r*W     : r*W+a]
B[r*b : (r+1)*b] → Y[r*W+a   : (r+1)*W]
```

这里的偏移以元素为单位。例如，`a=3、b=5` 时，A 中相邻两行的起点只相隔 3 个元素，在 Y 中却相隔 8 个元素。一次性读入 A 的多行，得到的仍是 A 的行序列，需要按输出步长写回，或者先在 UB 中把 A、B 交错排列成完整输出行。

对于连续存储的高维输入，可以把拼接轴之前的维度合并为行数，把拼接轴及其后面的维度合并为行宽，得到相同的问题：

```text
行数       = 拼接轴之前各维度的乘积
输入 j 行宽 = 输入 j 在拼接轴上的长度 × 该轴之后各维度的乘积
```

这样展开后，Tiling 要处理的主要参数就变成了行数、各输入行宽、元素字节数和输出行宽。沿第一维拼接对应行数为 1，可以优先考虑连续复制；行数很多、单路行宽很小时，则需要处理大量短片段。

对于窄行，有两种直接可比较的方案。第一种按输入组织搬运，将多行作为带步长的数据块写入输出；第二种先在 UB 中整理出多行拼接结果，再写回。后者减少了输出侧的碎片，但增加了重排和索引开销。官方的[内存优化文章](https://www.hiascend.com/zh/developer/techArticles/20240823-1)也通过前后数据流对照分析额外搬运的成本。

本文后续分析的 Concat 实现把若干路输入合成一组，并为每个核设置独立的 GM 临时区：先连续读取各输入的若干行并打包到临时区，再读回 UB，通过 Gather 按索引选取元素，整理成输出布局。对于 D 字节有效数据，这条路径显式请求的 GM 读写量约为 4D：读取输入、写入临时区、读取临时区、写入输出。直接复制的对应量为 2D。

增加临时区并非没有代价。它是否值得，取决于访问组织改善所节省的时间能否覆盖新增读写和重排；临时区的缓存命中还会影响片外高带宽内存（HBM）的实际流量。这里只计算算法请求的字节量，不据此推算硬件带宽利用率。

类似的分析也适用于广播。例如 `y[m,n] = x[m,n] + b[n]`，同一段 b 可以保留在 UB 中供多行复用，减少显式搬入次数，但也会占用原本可分配给 x 和 y 的空间。是否缓存、一次处理几行，要放在同一份 UB 预算里计算。

## 2. 分核时先确定任务粒度

如果每个核负责一段连续输出行，各核之间通常比较容易划清写入范围。假设每 R 行构成一个任务，M 行需要的任务数为：

```text
K = (M + R - 1) // R
```

这里 `R > 0`。在任务成本相近时，可以把 K 个任务分给 P 个核，前 `K % P` 个核多处理一个任务。第 i 个核的范围可写为：

```text
q     = K // P
r     = K % P
count = q + (i < r)
begin = i*q + min(i, r)
end   = begin + count
```

其中 `P > 0，0 ≤ i < P`，任务区间为 `[begin, end)`。例如，128 个任务使用 10 个核，前 8 个核各处理 13 个任务，后 2 个核各处理 12 个任务。

这个分法平衡的是任务数量。在 Concat 中，如果各任务包含的输入路数和片段宽度差别很大，即使有效字节数相近，搬运批次和地址计算开销也可能不同。这时还要估计每个任务实际执行了多少次搬运、多少次重排，检查工作是否集中在少数核上。

任务粒度与核数也相互影响。R 较大时，单个任务可以合并更多行，但任务总数减少，可能无法覆盖所有可用核；R 较小时，更容易分散任务，却会增加循环与同步次数。因此，核数和每任务行数需要一起考虑。

对连续逐元素算子，划分通常更简单，可以按满足搬运对齐条件的数据块分配。IndexAdd 则是按索引把源数据累加到指定位置的算子，必须额外处理重复索引：多个输入更新可能指向同一个输出位置，直接均分输入并不能保证并发写入正确。

Host 侧可以根据 Shape 和平台信息生成上述划分，把每核范围、行步长等参数交给 Kernel。只与 Shape 有关的公共计算尽量放在 Host 侧，避免在每个 tile 中重复执行。核数和 UB 容量可通过 [PlatformAscendC](https://www.hiascend.com/document/detail/zh/canncommercial/850/API/ascendcopapi/atlasascendc_api_07_1027.html) 获取。

## 3. 先列出缓冲区，再计算 tile

核内 tile 的大小受 UB 容量限制，但占用 UB 的往往不只有输入和输出。

以 FP16 Add 为例，两个输入、一个输出都使用双缓冲，每个槽存 T 个元素，仅数据缓冲就需要 `2 × 3 × T × 2 = 12T` 字节。如果还有临时向量或 API 工作区，应先扣除它们，再计算 T 的上限。

前述 Concat 分组实现还需要一份 Gather 索引表，用来记录重排时从哪里取数据，以及构造索引时使用的临时数组。作为性能对照的原始版本中，相关分配如下，1 KiB 为 1024 字节：

| 缓冲区 | 分配量 |
|---|---:|
| 输入双缓冲 | 2 × 32 KiB |
| 输出双缓冲 | 2 × 32 KiB |
| Gather 索引表 | 32 KiB |
| 初始化临时向量 | 3 × 8 KiB |
| 合计 | 184 KiB |

因此，不能根据“输入加输出能放下”就继续增大 tile。索引表也会随 tile 增长，而且每份双缓冲都要分配两个槽。

这一版本还有一处可复用的空间。构造 Gather 索引表时，输入搬运尚未开始；索引表构造结束后，三个初始化临时向量不再使用。修改后的版本借用一个输入槽存放这些临时向量，完成初始化并同步后，再将这个槽用于输入搬运。索引表自身仍独立保留。

省掉独立的 24 KiB 临时区后，两个输入槽、两个输出槽和索引表都可以扩为 38 KiB，总分配为 `5 × 38 = 190 KiB`。这两个合计数是具体实现的显式分配量，不是芯片 UB 的规格。

复用的条件是前一个阶段已经完成对该区域的访问。修改后的实现通过同步事件，先确认构造索引的向量操作完成，再允许后续搬入覆盖输入槽。若只看 C++ 代码中的先后顺序，异步向量操作仍可能与后续搬入发生冲突。

确定单槽容量后，还要把它换算成实际处理几行。设组内有效行宽为 G 字节，UB 行步长为 `S = align_up(G, 32)`，即将 G 向上补齐到 32 的整数倍；单槽容量为 B。如果该路径按 8 行组织处理，则容量允许的行数为：

```text
R = 8 × floor(B / (8 × S))
```

式中的 `floor` 表示向下取整。这解释了为什么组宽只增加一点，tile 行数有时会突然减少 8 行：R 是离散取值。组数减少与每组 tile 数增加可能同时发生，需要重新计算任务总量。这里的 8 行是这一实现的选择，不能直接用于其他算子；若算出的 R 为 0，则当前槽容量无法容纳该分组。

最后一块数据可能不足一个完整 tile，这部分称为尾块，应单独保留有效长度。UB 中为了向量处理而补齐的部分，不一定对应合法的 GM 元素。搬入和写回时，需要按实际接口处理有效字节数，避免把填充区域当作有效输出。主块、尾块及分核之间的关系可参考官方[尾块 Tiling 示例](https://www.hiascend.com/document/detail/zh/CANNCommunityEdition/850/opdevg/Ascendcopdevg/atlas_ascendc_10_00009.html)。

## 4. 双缓冲需要与 tile 一起设计

常见的 Vector 路径通过 MTE2 将数据搬入 UB，Vector 执行计算或重排，再由 MTE3 写回 GM。双缓冲为相邻 tile 提供独立存储，使后一块的搬入有机会与前一块的处理重叠。各执行单元及队列之间的关系见官方[流水优化说明](https://www.hiascend.com/zh/developer/techArticles/20240819-1)。

在 Concat 的重排阶段，当前输入槽还要供 Gather 读取。如果只有一个输入槽，下次搬入就必须等到本次 Gather 不再访问它；有两个槽时，可以在处理当前 tile 前，先向另一个槽发起下一次读取。

但增加槽数会占用 UB。固定总容量下，双缓冲可能要求更小的 tile，从而增加搬运批次。对于每核只有一个 tile 的小输入，额外槽位也没有相邻任务可供重叠。

另一个实验方案保留输出双缓冲，将输入减少为单槽，单槽容量从 38 KiB 增至 47.5 KiB，允许的分组宽度继续扩大。这个方案减少了部分输出任务，但无法保留原来的输入预取顺序，即在处理当前块时提前读取下一块数据。

该方案同时改变了组宽、槽大小和预取，需要结合完整耗时判断效果，测量结果放在第 6 节。扩大 tile 所得到的循环次数收益，可能被减少重叠机会所抵消。若要单独分析双缓冲的贡献，应固定组宽比较输入槽数，或固定缓冲方案比较组宽。

对于纯复制阶段，还可以检查是否存在不必要的 UB→UB 复制。官方[API 使用优化文章](https://www.hiascend.com/developer/techArticles/20241107-1)展示了用 TQueBind 关联搬入、搬出阶段的做法。它适用于无需改变数据布局的部分；Concat 中承担实际重排的 Gather 不能因此省略。修改队列和内存复用方式时，相应的同步依赖也要重新检查。

## 5. 不同输入可以选择不同实现

到这里，同一个算子采用多条路径就有了依据。对于 Concat，可以根据连续片段的长度、行数及对齐情况，分别选择连续复制、带步长搬运或分组重排。小输入则可能更适合初始化和队列操作较少的实现。

这些条件应能从输入属性推导出来。例如，某条 Gather 路径按 32 位元素组织，就要检查输入位宽和相关行宽是否满足要求；需要索引表常驻 UB，就要计算它与输入输出缓冲同时存在时的容量。条件不满足时，回到通用实现。

Greater 逐元素判断第一个输入是否大于第二个输入，输出布尔结果，也需要考虑广播形式。标量与整个张量比较、向量按行广播、两个同形状张量逐元素比较，重复读入的数据不同，值得分别处理。仅仅为了减少指令而转换数据类型，可能改变比较结果：16777216 与 16777217 在转成 FP32 时就可能失去原有的大小区别。

分支带来性能机会，也增加验证工作。测试除了检查输出，还应确认输入进入了预期路径，覆盖条件边界及回退分支。否则，一个始终走旧实现的用例，无法验证新增路径。

## 6. 用逐例结果检查优化是否符合预期

下面引用 Concat 赛题开发过程中的一组本地对照，观察前述分组调整是否有效。这组测试包含五种固定输入配置，每种配置的 Shape、数据类型和拼接轴在版本对比时保持不变。以下数据用于分析实现变化，不能代替赛事平台的评测成绩。

将原实现记为 A，将复用初始化空间、扩大分组后的版本记为 B。在第 5 组输入上，B 的输出 tile 数由 2520 降为 2016，减少 20%，因此重点观察这组输入的耗时。同时测试其余配置，检查是否出现退化。

两种版本按 A—B—B—A 顺序运行，每次覆盖全部五组输入。下表列出第 4、5 组以及五组耗时之和；编号只用于区分本实验的输入配置。

| 顺序 | 输入配置 4（μs） | 目标输入配置 5（μs） | 五组耗时合计（μs） |
|---|---:|---:|---:|
| A1 | 83.2020 | 193.7440 | 326.5270 |
| B1 | 78.2415 | 193.7435 | 319.8560 |
| B2 | 81.0820 | 192.8640 | 321.6280 |
| A2 | 79.0410 | 195.1935 | 321.6455 |

从 A1 到 B1，合计耗时下降了 6.6710 μs，其中第 4 组输入下降了 4.9605 μs，目标输入几乎不变。第二次测量中，修改前后的合计耗时又非常接近。这组结果不足以证明减少输出 tile 带来了稳定收益，因此保留了原实现。

第 4 节提到的 47.5 KiB 输入单槽方案，也在同一测试集上做了测量，五组耗时合计为 356.2865 μs，未获得收益。它同时改变了分组和预取，不能将全部退化归因于减少一个输入槽。

这张表也提示了后续分析方向：分组变化还会改变输入打包批次、尾块和每核负载，不能只统计输出 tile。如果继续尝试，应把这些工作量一起列出，再用时间线检查新增等待发生在哪个阶段。

这组测试对每种输入执行 30 轮，每轮先运行一个辅助的逐元素乘法算子 Mul，再调用 Concat。统计时仅保留 Concat 记录，按原顺序取第 11 至 30 条记录的中位数，并保留计时脚本中的整数转换顺序。辅助调用和轮数在各版本之间保持一致。表中小数位来自该统计方式，不代表同等测量精度。测量期间避免其他任务占用同卡。

正确性检查在计时之前完成，尤其是尾块、非对齐行宽和新增路径的边界。不同版本各自最快的单项结果也不能合并成总耗时，最终对照需要来自同一个完整实现。

入门阶段可以先保留一个简单、正确的通用版本，围绕一种输入布局改进它。地址计算、分核范围、UB 占用和计时结果都能明确对应到代码时，下一轮改动才有可比较的依据。若这些局部参数已经反复调整过，剩下的主要成本仍来自同一种访问方式，就需要进一步考虑改变分组、布局或处理阶段。
