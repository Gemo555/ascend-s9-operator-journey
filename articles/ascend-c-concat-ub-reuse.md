# Concat 优化实录：UB 复用省下的空间，为什么没有换来稳定提速

本文的案例来自[昇腾 AI 创新大赛——算子挑战赛 S9 赛季](https://www.hiascend.com/developer/contests/details/41ffbad2024e4ccfa43520c57ffa7b9e)中的 Concat 赛题。题目要求使用 Ascend C 将一组输入张量沿指定轴按顺序拼接，输入在拼接轴上的长度可以不同，其他对应维度保持一致，输出保留元素值及其排列顺序。

对于沿末维拼接的连续输入，一路输入在输出中可能对应许多短片段。我们实现了一条分组路径：先将多路输入打包到临时区，再在 UB 中重排成输出布局。本文讨论的优化发生在这条以 32 位元素为处理单位的路径上，实验环境为 Ascend 910B4、CANN 8.5.0。

目标测试输入包含 137 路 FP32 张量，沿第二维拼接后输出为 `[2012,8811]`。其中两路长度为零，非空输入的单行宽度最大为 512 B。许多短片段需要写入同一个较宽的输出行，这正是分组实现试图改善的访问形态。

一次修改复用了初始化临时区，将单个数据槽从 32 KiB 扩大到 38 KiB，并提高了分组宽度上限。目标输入的输出 tile 数从 2520 降到 2016，减少了 20%，最终却没有得到稳定的延迟改善。下面从这条路径实际占用的缓冲区解释原因。

## 1. 先确认省下的空间将用在哪里

把连续输入展平成 H 行，输入 j 的每行宽度记为 bⱼ 字节。若将相邻的几路输入合成一组，这组的有效行宽为 G，行内前缀偏移为 Pⱼ：

```text
G = Σ bⱼ
Pⱼ = Σ bᵢ，i < j，求和范围为当前组
```

实现为每个核安排了独立的 GM workspace，处理一个行带时分成两个阶段：

```text
Pack：    输入 GM → 输入 UB → 输出 UB → 私有 workspace
Regroup： workspace → 输入 UB → Gather → 输出 UB → 输出 GM
```

Pack 连续读取某一路输入的多行，workspace 中按输入依次存放。Regroup 再把同一行的各路片段整理到一起，按输出行间隔写回。

这样组织增加了临时区读写。忽略填充，对 D 字节有效数据，显式请求的 GM 读写量约为 4D：读输入、写临时区、读临时区、写输出；直接复制对应 2D。4D 描述的是这条算法路径的访问量，workspace 的缓存命中会影响实际片外流量，不能据此直接计算 HBM 带宽。

分组后一次写回可以覆盖更宽的输出片段，但 UB 同时需要容纳输入、输出和 Gather 索引。优化空间就在这里：若能保留原来的输入预取和输出缓冲，同时扩大每个槽，是否可以合并更多输入，减少输出任务？

## 2. 初始化临时区与输入数据不需要同时存在

原实现除双输入、双输出和一份 map 外，还分配了三份临时向量，用于构造 Gather 索引。以 KiB 为单位，显式分配如下：

| 区域 | 原实现 | 复用后的候选 |
|---|---:|---:|
| 输入队列 | 2 × 32 | 2 × 38 |
| 输出队列 | 2 × 32 | 2 × 38 |
| Gather map | 32 | 38 |
| 初始化临时向量 | 3 × 8 | 借用一个输入槽 |
| 合计 | 184 | 190 |

这里的合计是源码中这些缓冲区的分配量，1 KiB = 1024 B，不是设备 UB 总容量的规格说明。

三个临时向量只在 `InitIndices` 和 `BuildMap` 中使用，此时输入数据还没有搬入。map 构造完成后，临时向量不再参与计算；map 本身则需要在后续每个 tile 中使用，不能一起覆盖。

因此，候选从输入队列申请一个槽，把三份 8 KiB 临时向量放进去。索引构造结束后释放这个槽，后续再作为输入缓冲使用。省去的独立临时区为 24 KiB；五份常驻数据区各增加 6 KiB，共增加 30 KiB，所以最终分配量比原实现增加了 6 KiB。

关键依赖在临时向量的最后一次使用。冻结代码在释放槽之前执行 `V_MTE2` 的 `SetFlag/WaitFlag`，确保构造索引的向量操作完成，再允许后续输入搬入覆盖它。生命周期应按执行单元的实际访问来判断，不能只看 C++ 变量离开作用域，或者 `BuildMap` 已经返回。

```text
初始化阶段：输入槽 0 = row | col | work
                         ↓ 构造独立 map
                 等待向量操作完成
数据处理阶段：输入槽 0 = 输入数据；输入槽 1 可用于预取
              map 持续保留
```

类似的复用也适用于建表、转置或归约中的临时区。具体实施时要核对两件事：旧数据的最后一个消费者何时结束，新数据的第一个写入者何时开始。若为了复用而增加了等待，节省的容量还需要覆盖这部分代价。

## 3. 组更宽，tile 行数会跟着变化

在这条实现中，输出 UB 的行步长为 `S=align_up(G,32)`，tile 行数 R 取 8 的倍数。忽略总行数对 R 的截断，单槽容量 B 给出：

```text
R = 8 × floor(B / (8 × S))
```

这里各输入行宽都是 4 字节的整数倍，R 取 8 的倍数后，完整 tile 内每路输入的 `R×bⱼ` 都能按 32 字节单位组织 Pack。这是当前数据布局的选择。

为了让非空组至少容纳 8 行，需要 `8S ≤ B`。单槽从 32768 B 增加到 38912 B 后，允许的组宽上限从 4096 B 增加到 4864 B。注意两个上限描述的对象不同：B 是整个槽的容量，G 是一行中这一组输入的有效宽度。

更宽的组有机会减少组数，但对某个确定的组，S 增大也会让 R 阶梯式下降。因此，输出 tile 总数需要重新按照实际分组、分核和尾行计算。2520 到 2016 是目标输入的具体结果，无法仅由 32 KiB 到 38 KiB 的比例推出。

改变 R 还会改变 Gather 映射。对于组内输入 j 的第 r 行、第 c 个 32 位元素，当前完整 tile 的映射为：

```text
workspace 字节偏移 = R×Pⱼ + r×bⱼ + 4c
输出 UB 字节偏移  = r×S + Pⱼ + 4c
map[(r×S + Pⱼ + 4c) / 4] = R×Pⱼ + r×bⱼ + 4c
```

map 的下标按元素计数，内容保存字节偏移。假设三路行宽分别为 12、20、4 B，R=8，则 G=36、S=64。第二路输入的第 3 行、第 2 个元素，按零起始编号，对应 `map[53]=164`。如果只扩大缓冲区，却沿用旧的 R 构造 map，就会把正确数据搬到错误位置。

下面的独立 Python 示例可以检查这个完整 tile 的布局关系；它不模拟设备同步和尾块搬运：

```python
rows = 8
widths = [3, 5, 1]  # uint32 元素数
stride_bytes = (sum(widths) * 4 + 31) // 32 * 32
stride = stride_bytes // 4
inputs = [[[j * 10000 + r * 100 + c for c in range(w)]
           for r in range(rows)] for j, w in enumerate(widths)]
packed = [v for tensor in inputs for row in tensor for v in row]
offsets = [0] * (rows * stride)
prefix = 0
for j, width in enumerate(widths):
    for r in range(rows):
        for c in range(width):
            dst = r * stride + prefix + c
            offsets[dst] = 4 * (rows * prefix + r * width + c)
    prefix += width
gathered = [packed[offset // 4] for offset in offsets]
for r in range(rows):
    expected = [v for tensor in inputs for v in tensor[r]]
    assert gathered[r * stride:r * stride + sum(widths)] == expected
assert offsets[53] == 164
```

## 4. 输出 tile 少了，Pack 侧发生了什么

对于当前行带，设 F 为完整 tile 数。一路输入每个 tile 有 `R×bⱼ` 字节，一个容量为 B 的输入槽可以连续装下：

```text
mⱼ = floor(B / (R×bⱼ)) 个完整 tile
```

源码会将这些完整 tile 合成批次搬运，最后单独处理尾行。跳过零长度输入后，这一路的 Pack 任务数可以写成：

```text
qⱼ = ceil(F / mⱼ) + I(存在尾行)
```

所以输出 tile 数下降，并不代表输入侧所有任务也按相同比例减少。组边界、R、每路行宽和每核行带都可能改变批次数；map 初始化、workspace 访问以及阶段间等待也仍然存在。

这轮实验还尝试过按 Pack 批次数重新划分宽组。离线计数改善了，但五例总耗时达到 339.947 μs，没有胜出。原因尚不能仅靠任务数确定：一条短搬运和一条长搬运的延迟不同，不同核的等待也不同，未经校准的批次数不能直接用作完整延迟模型。

## 5. 同卡对照没有支持替换基线

我们将原实现记为 A，将“复用初始化临时区并扩大分组”的候选记为 B。两者对同样的五种固定输入配置进行 A—B—B—A 交替测试。每例保留原扩展的 30 轮调用，统计排除辅助 Mul，取原顺序第 11 至 30 轮的中位数，并保留原脚本的整数转换细节。

表中的第 5 例就是开头介绍的 137 路 FP32 输入；第 4 例为五路 INT32 输入沿轴 1 拼接，输出为 `[1077,12,663]`，其中包含一路零长度输入。

| 运行顺序 | 第 4 例（μs） | 目标第 5 例（μs） | 五例合计（μs） |
|---|---:|---:|---:|
| A1 | 83.2020 | 193.7440 | 326.5270 |
| B1 | 78.2415 | 193.7435 | 319.8560 |
| B2 | 81.0820 | 192.8640 | 321.6280 |
| A2 | 79.0410 | 195.1935 | 321.6455 |

第一次比较时，总和减少了 6.6710 μs，但其中 4.9605 μs 来自第 4 例，目标第 5 例几乎未变。只看第一次总和，很容易把其他输入上的变化也记到目标路径上。

继续看两轮结果，候选较慢的一次为 321.6280 μs，基线较快的一次为 321.6455 μs，仅差 0.0175 μs；两次基线自身相差 4.8815 μs。按当时使用的保守筛选条件，候选没有进入替换基线的后续发布回归。两轮对照还不足以确定微小收益，只能说明这一轮没有获得足够稳定的改进证据。

为了区分容量与分组的影响，我们还测了只扩大槽、保留原分组的版本。另一组交替对照中，基线总和为 323.0175 / 324.9260 μs，候选为 324.5360 / 325.8055 μs，也没有胜出。由此仍不能推断 UB 复用在其他场景无效，但没有理由把它直接作为这个实现的新默认配置。

## 6. 再扩大槽位，会碰到流水的代价

另一个候选把输入槽减为一个，保留两个输出槽和一份 map。四份缓冲各为 47.5 KiB，合计仍为 190 KiB，组宽上限可以提高到 6080 B。

代价出现在 Regroup 调度中：双输入版本能够先发起下一 tile 的读取，再处理当前 tile；单输入槽需要等当前消费者完成后才能覆盖这个槽。输出侧仍可能与其他阶段重叠，因此不能将它描述成整个 Kernel 都串行了。

该候选五例合计为 356.2865 μs，目标用例为 225.3140 μs，明显退化。但它同时改变了输入槽数、单槽大小和组宽，这个结果只能评价整组修改；若要量化输入预取的贡献，还需要固定其他条件再对照。官方的[流水优化文章](https://www.hiascend.com/zh/developer/techArticles/20240819-1)也将双缓冲收益与数据规模、搬运及计算时间联系起来，不能仅凭槽数判断快慢。

这次复用在内存布局上成立，在设备正确性检查中也通过了验证。它没有形成稳定性能收益，说明省出的空间能否转化为速度，还取决于用这些空间换来了什么：更少的有效任务、更均衡的分核，还是更大的 tile 和更长的等待。今后遇到 UB 紧张时，我们仍会检查临时区的使用阶段，但会同时记录 Pack 批次、输出任务和可重叠的读写关系，再用完整计时决定是否保留。
