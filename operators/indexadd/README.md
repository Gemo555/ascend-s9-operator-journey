## 题目与版本

以 `self` 为初值，沿 `dim` 将 `source` 的切片累加到 `index` 指定的位置。重复索引涉及同一输出的多次更新，需要同时处理输出所有权和数值顺序。

当前可追溯的本地收尾包为 **P151**，同场完整五例两次为 **650.883499 / 649.0425 μs**，对应 P135 为 668.3845 / 658.722499 μs。已有榜单的 631.569999 μs 尚未与具体 ZIP 对齐，不能称为 P151 的官方结果。

## 核心设计

按输出行划分互不重叠的工作，为每个目标列建立按源位置递增的来源计划。不同列之间可以并行，单列内部仍保留原更新顺序。根据更新深度重排列，可以让每层仍需更新的列形成活动前缀。

P151 的 FP32 路径每次处理 8 行，将源分块从 `[8,C]` 转为 `[C,8]`。同一来源位置的 8 个 FP32 值连续占 32 B，可以使用 Gatherb 按块取数。累加器跨源分块驻留，块间仍按原顺序处理，最终恢复输出行布局。

关键改进发生在转置完成之后：raw 源缓冲已不再使用，便将它分成 Gather 结果区与常驻计划区。目标输入的 C 从 1536 扩为 2560，4960 个来源位置从四块减少为两块。

```text
raw：搬入 8 行源数据 → 局部转置到 transposed
raw：等待旧读取完成 → Gather 结果 | 常驻索引计划
                          ↓
                  保序累加到 acc
```

目标计算阶段布局为 184864 B，统一 UB arena 为 190016 B。容量和实际重复深度不满足条件时回退已有路径，不能用平均重复次数代替最坏容量检查。

## dtype 路径与正确性

P135 已合入 INT8 输出行块驻留和 half 源读取调整；P151 主要改变 FP32 路径。BF16 路径保留每次更新后的舍入，连续搬入紧凑源行，仅对当前核需要的未对齐行做短 Gather，再执行原 Cast/Add/Cast。

这些修改依赖具体参考实现的数值行为。把 BF16 全程升为 FP32、最后只舍入一次，可能改变结果；改变浮点重复更新的顺序也可能改变结果。

P151 历史发布记录包含 6 项逐位专项、54 项预检、156 项完整检查及 153 项发布回归。这里引用已有记录；本仓库初始化没有重新运行 NPU 测试。
